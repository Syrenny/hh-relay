## Цель

Добавить к существующему hh-relay простой однопользовательский сервис поиска работы:

- GitHub Actions запускает мониторинг каждый час в активное время;
- новые вакансии сохраняются в PostgreSQL и один раз оцениваются через OpenAI API;
- при появлении подходящих вакансий пользователю отправляется email;
- закрытая веб-страница показывает список вакансий и позволяет отметить `интересная`, `откликнулся`, `не подходит` или `архив`;
- для выбранной вакансии по кнопке генерируется и сохраняется сопроводительное письмо;
- OpenAI API используется с добровольно включённым data sharing, чтобы подходящий трафик мог расходовать complimentary tokens.

Специально не добавлять отдельную очистку или маскирование персональных данных. Профиль кандидата и публичные карточки вакансий передаются модели напрямую по явному решению пользователя. Секреты, API keys и пароли по-прежнему никогда не передаются модели и не записываются в Git или логи.

## Принцип минимальной сложности

Не создавать отдельный frontend-проект, очередь задач, административную панель, конструктор фильтров или несколько сервисов приложения.

Использовать:

- текущий FastAPI deployment на Vercel;
- серверный HTML через Jinja2, Web Awesome и небольшой обычный JavaScript;
- один PostgreSQL Neon, подключённый через `DATABASE_URL`;
- версия схемы PostgreSQL управляется Alembic, миграции применяются до запуска monitor;
- один Python-скрипт мониторинга в этом репозитории;
- GitHub Actions как планировщик и исполнитель длительной задачи;
- OpenAI Responses API для оценки и писем;
- Resend HTTP API для email;
- HTTP Basic Authentication для единственного пользователя dashboard.

Мониторинг выполняется в GitHub Actions, поэтому не зависит от текущего `maxDuration=30` Vercel Function. В Vercel остаются быстрые dashboard-запросы и один вызов OpenAI для генерации письма.

## Пользовательский сценарий

1. Почасовой workflow ищет вакансии по фиксированным запросам из `skills/find-python-backend-jobs/SKILL.md`.
2. Уже известные vacancy ID отбрасываются по уникальному ключу в БД.
3. Для новых правдоподобных кандидатов загружаются полные карточки.
4. OpenAI возвращает структурированную оценку: `strong`, `debatable` или `skip`, краткое обоснование, требования и предупреждения.
5. Все оценённые вакансии появляются в dashboard. В email попадают только новые `strong` и `debatable`.
6. Пользователь меняет статус карточки одной кнопкой.
7. Кнопка `Сгенерировать письмо` отправляет полную карточку и профиль кандидата в OpenAI, показывает сохранённый черновик и позволяет скопировать его.

Если новых подходящих вакансий нет, workflow не отправляет письмо. Ошибка запуска отображается в GitHub Actions и сохраняется в `monitor_runs`; отдельные сервисные письма об успехе не отправляются.

## Поиск и оценка

Переиспользовать правила `skills/find-python-backend-jobs/SKILL.md`:

- `Python backend` + `noExperience`;
- `Python backend` + `between1And3`;
- `Django Python` + `between1And3`;
- `FastAPI Python` + `between1And3`;
- сначала поиск без area, при `truncated=true` дополнительный поиск для Новосибирска и Москвы;
- дедупликация по vacancy ID;
- явный шум по названию отбрасывается до полной карточки;
- полная оценка опирается только на `get_vacancy`.

Чтобы контролировать время и токены, за один запуск загружать и оценивать не более 15 новых наиболее правдоподобных карточек. Остальные новые ID не считать окончательно просмотренными: следующий запуск должен иметь возможность взять их в обработку.

Оценку выполнять одним пакетным Responses API запросом со Structured Outputs, а не отдельным запросом на каждую вакансию. HTML описаний преобразовывать в обычный текст только для уменьшения шума и расхода токенов, не для удаления персональных данных.

Карточки вакансий считать недоверенными данными. Инструкции внутри описания не должны изменять системные правила, раскрывать secrets или инициировать внешние действия.

## Сопроводительные письма

Переиспользовать без смыслового расхождения:

- `skills/write-python-cover-letter/SKILL.md`;
- `skills/write-python-cover-letter/candidate-profile.md`;
- `skills/write-python-cover-letter/writing-preferences.md`.

Содержимое этих файлов загружать сервером как prompt context. Не дублировать профиль и правила в нескольких Python-строках.

Генерация происходит только по нажатию пользователя. Ответ должен быть структурированным:

- готовый текст письма либо `null`;
- предупреждение о блокирующем несоответствии;
- особое требование работодателя к отклику;
- короткий вопрос пользователю, если для письма не хватает обязательного факта.

Черновик сохраняется в БД. Кнопка повторной генерации явно создаёт новую версию; отправка отклика на hh.ru не автоматизируется.

## Данные

Минимальная схема PostgreSQL:

### `vacancies`

- `id` — vacancy ID, primary key;
- название, компания, URL, зарплата, город, время публикации;
- нормализованный текст полной карточки и исходные структурированные поля;
- оценка модели, обоснование и ключевые требования;
- пользовательский статус: `new`, `interesting`, `applied`, `not_suitable`, `archived`;
- `first_seen_at`, `evaluated_at`, `updated_at`.

### `cover_letters`

- внутренний ID;
- vacancy ID;
- текст, предупреждение, особое требование и вопрос;
- модель и время генерации.

### `monitor_runs`

- начало, окончание, статус;
- количество найденных, новых, оценённых и отправленных вакансий;
- безопасный текст ошибки без secrets и полного upstream body.

Отдельные таблицы пользователей, поисковых запросов и истории каждого клика не добавлять. Фиксированных запросов и одного текущего статуса достаточно.

Схему оформить миграциями Alembic и отдельной командой инициализации. Не создавать таблицы скрыто при каждом HTTP-запросе.

## Веб-интерфейс

Добавить закрытые маршруты:

- `GET /dashboard` — список с новыми сверху;
- `POST /dashboard/vacancies/{id}/status` — смена статуса;
- `GET /dashboard/vacancies/{id}` — полная карточка, оценка и письмо;
- `POST /dashboard/vacancies/{id}/cover-letter` — генерация новой версии письма.

На главной странице оставить только:

- основной список нескрытых вакансий и один переключатель на скрытые;
- название, компания, зарплата, возраст вакансии и оценка;
- ссылка на hh.ru;
- одну кнопку «Скрыть» или «Вернуть»;
- счётчик использованных за текущий день токенов OpenAI.

Для визуального слоя использовать Web Awesome как framework-agnostic библиотеку Web Components: карточки, кнопки, badges, tabs, dialogs, alerts и состояния загрузки. Подключить зафиксированную версию, добавить небольшой собственный CSS для сетки и адаптивности. Интерфейс должен удобно работать на телефоне и компьютере. Отдельные React/Next.js приложение, Node build pipeline и JSON API для frontend не добавлять.

Не добавлять поиск, сортировки, графики, настройки модели, редактирование профиля или визуальный конструктор запросов.

Защита dashboard:

- `DASHBOARD_USERNAME` и `DASHBOARD_PASSWORD` в Vercel environment;
- HTTP Basic поверх обязательного HTTPS;
- constant-time сравнение credentials;
- проверка `Origin`/`Host` для POST-запросов;
- OpenAI, database и Resend credentials никогда не попадут в HTML.

## Email

После успешной оценки отправлять одно HTML-письмо только при наличии новых `strong` или `debatable` вакансий.

Для каждой позиции указать название, компанию, зарплату, возраст, оценку, краткое объяснение, ссылку на hh.ru и ссылку на dashboard. Письмо не должно содержать полные описания вакансий.

Использовать `RESEND_API_KEY`, `EMAIL_FROM`, `EMAIL_TO` из GitHub Actions secrets. Ошибка email не должна помечать вакансии как неоценённые и приводить к повторному расходу OpenAI; повторную доставку можно выполнить ручным перезапуском с идемпотентной логикой.

## Расписание GitHub Actions

Создать workflow с `workflow_dispatch` и cron:

- каждый час с 07:17 до 23:17 по Новосибирску;
- один дополнительный ночной запуск;
- `concurrency` запрещает перекрытие двух monitor runs;
- timezone фиксируется комментариями в UTC cron expression.

Workflow устанавливает зависимости через `uv`, запускает миграцию и monitor script. Secrets:

- `DATABASE_URL`;
- `OPENAI_API_KEY`;
- `RESEND_API_KEY`;
- `EMAIL_FROM`;
- `EMAIL_TO`;
- `DASHBOARD_BASE_URL`.

`HH_ACCESS_TOKEN` workflow не нужен: мониторинг обращается к публичным REST endpoints развёрнутого hh-relay. URL задаётся как `HH_RELAY_BASE_URL`, с production URL по умолчанию.

## OpenAI и контроль расходов

Использовать отдельный OpenAI project и его API key. В API Platform пользователь самостоятельно включает sharing inputs/outputs для этого project/organization и проверяет, что выбранная модель участвует в программе complimentary tokens.

По умолчанию использовать подтверждённую условиями аккаунта модель `gpt-5.4-mini`. Переменная `OPENAI_MODEL` остаётся необязательным override, чтобы смена списка eligible models не требовала изменения кода.

Каждый запуск сохраняет фактические input/output token usage из ответа OpenAI. Добавить программный дневной предел `OPENAI_DAILY_TOKEN_BUDGET`; при его достижении новые вакансии остаются ожидающими оценки, а платный fallback на другую модель не выполняется. Это исключает незаметный выход за выбранный бесплатный объём.

## Проверки и критерии приёмки

- Повторный monitor run не оценивает и не отправляет одну vacancy повторно.
- Параллельный/повторный workflow безопасен благодаря DB constraints и concurrency.
- При отсутствии новых подходящих вакансий email не отправляется.
- Dashboard недоступен без корректного Basic Auth.
- Статусы меняются только допустимыми значениями и сохраняются после redeploy.
- Список содержит рабочие ссылки на hh.ru и страницы вакансий.
- Генерация письма использует полную карточку, профиль и writing preferences из skill.
- Письмо не выдумывает опыт и соблюдает формат, длину и запрет длинных тире.
- Ни dashboard, ни логи не раскрывают API keys, database URL или пароли.
- Дневной token budget предотвращает платный fallback после исчерпания заданного объёма.
- Ruff, все тесты и `git diff --check` проходят.

Production smoke test должен подтвердить ручной запуск workflow, запись вакансий в Neon, dashboard, смену статуса, генерацию письма и доставку одного тестового email.

4. Добавить перечисленные environment variables и GitHub Actions secrets.
5. Выбрать `DASHBOARD_USERNAME` и сильный `DASHBOARD_PASSWORD`.

## Риски и восстановление

- GitHub scheduled runs могут задерживаться. Поиск за 24 часа и дедупликация не дают потерять вакансии из-за небольшой задержки.
- Бесплатные модели или квоты OpenAI могут измениться. `OPENAI_MODEL` и дневной бюджет позволяют адаптироваться без переписывания workflow.
- Включённый data sharing разрешает OpenAI использовать профиль, вакансии и ответы для улучшения моделей. Это принято пользователем; secrets всё равно исключаются.
- HTTP Basic подходит для одного пользователя и минимального интерфейса, но не для публичного многопользовательского продукта. При расширении потребуется полноценная авторизация.
- Если email не доставлен, вакансии сохраняются в dashboard; мониторинг остаётся полезным без почты.
- Rollback к текущему relay выполняется возвратом commit. Новые dashboard routes и monitor workflow не меняют публичные REST/MCP контракты.
