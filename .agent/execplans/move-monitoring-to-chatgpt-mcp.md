## Цель

Убрать зависимость мониторинга от платного OpenAI API. Поиск, чтение полных карточек и смысловой отбор выполняет запланированная задача ChatGPT через подключённый MCP. Отобранные вакансии ChatGPT сохраняет новым MCP tool в Neon, после чего пользователь просматривает их в существующем dashboard.

Рейтинг заменить на tier list:

- `S` — приоритетный отклик, сильное совпадение;
- `A` — хорошее совпадение, стоит откликнуться;
- `B` — допустимый вариант с заметными оговорками;
- `C` — слабый, но всё ещё сохранённый для ручного решения.

ChatGPT не должен сохранять заведомо неподходящие вакансии. На dashboard tier идут в порядке `S`, `A`, `B`, `C`, а внутри tier — от новых публикаций к старым.

## Архитектура

Оставить один FastAPI deployment на Vercel, существующий MCP endpoint, Neon PostgreSQL и server-rendered dashboard.

Поток одного запуска:

1. Scheduled task ChatGPT применяет обновлённый skill поиска.
2. ChatGPT вызывает `search_vacancies` по заданным запросам и дедуплицирует ID.
3. Для правдоподобных кандидатов ChatGPT вызывает `get_vacancy` и оценивает полную карточку относительно профиля пользователя.
4. Все обработанные позиции одним или несколькими небольшими batch передаются в новый `save_classified_vacancies`, включая неподходящие с классификацией `rejected`.
5. Сервер не доверяет присланным названию, ссылке или описанию: по каждому ID повторно получает каноническую карточку через официальный API hh.ru.
6. Сервер идемпотентно сохраняет карточку, tier, краткое обоснование, требования и предупреждения.
7. Dashboard группирует нескрытые вакансии по tier. Кнопка «Скрыть» и отдельный просмотр скрытых сохраняются.

GitHub Actions больше не запускает мониторинг. OpenAI Responses API и Resend не участвуют в runtime.

## MCP-контракт

Добавить структурированный write-tool:

```text
save_classified_vacancies(vacancies: list[ClassifiedVacancy]) -> SaveClassifiedVacanciesResult
```

Один элемент содержит:

- `vacancy_id` — положительный ID hh.ru;
- `tier` — `S`, `A`, `B`, `C` или `rejected`;
- `rationale` — короткое объяснение выбора;
- `requirements` — важные требования, подтверждённые карточкой;
- `warnings` — реальные риски или вопросы для ручной проверки.

Tool возвращает списки/счётчики `created`, `updated`, `unchanged` и безопасные ошибки отдельных ID. Повторная передача одного ID не создаёт дубль. Если вакансия уже скрыта пользователем, повторный запуск обновляет её данные и оценку, но не возвращает в основной список. Успешно сохранённые `rejected` не показываются в dashboard, но исключаются из последующих MCP-поисков.

Аннотации MCP должны явно указывать, что tool изменяет состояние, является идемпотентным и не является destructive. Инструкции самого MCP дополняются обязательным вызовом сохранения только после чтения полной карточки.

## Защита write-tool

Текущий пользовательский MCP подключён без OAuth. Полноценный OAuth 2.1 для одного личного сервиса непропорционально усложнит приложение, поэтому в первой версии write-tool остаётся доступен через тот же endpoint, но получает жёсткие серверные границы:

- только канонические ID и данные, повторно загруженные с hh.ru;
- не более 15 элементов за один вызов;
- только вакансии, опубликованные недавно в допустимом окне поиска;
- строгие enum и ограничения длины всех текстовых полей;
- idempotent upsert по ID;
- запрет изменения пользовательского признака `archived`;
- никакого произвольного JSON, HTML или URL от вызывающей модели;
- безопасные логи без полного описания вакансии и секретов.

Это не полноценная аутентификация: знающий публичный MCP URL клиент теоретически сможет сохранить настоящие свежие вакансии hh.ru. Риск ограничен публичными данными и принят для минимальной личной версии. Перед появлением чувствительных данных или нескольких пользователей обязательно добавить OAuth 2.1 либо вынести endpoint за аутентифицирующий proxy.

## Dashboard

Главная страница остаётся простой:

- без токен-счётчика;
- без генерации через OpenAI API;
- нескрытые вакансии сгруппированы в секции `S`, `A`, `B`, `C`;

- карточка содержит tier, название, компанию, зарплату, город, краткое обоснование, время публикации и ссылки;

## Критерии приёмки

- ChatGPT может сохранить batch выбранных вакансий одним MCP-вызовом.
- Сервер хранит только карточки, подтверждённые официальным API hh.ru.
- Некорректный tier, слишком большой batch и чрезмерно длинные тексты отклоняются валидацией.
- Повторный вызов не создаёт дубли и не возвращает скрытую вакансию.
- Dashboard показывает `S/A/B/C` в правильном порядке и не содержит OpenAI token counter.
- Без `OPENAI_API_KEY`, Resend secrets и GitHub workflow основной сценарий полностью работает.
- `search_vacancies` и `get_vacancy` сохраняют обратную совместимость.
- Обновлённый skill в ручном тесте вызывает сохранение и не подчиняется инструкциям из описаний вакансий.
- Dashboard по-прежнему закрыт HTTP Basic, а POST-защита и скрытие работают.
- Ruff, все тесты, `git diff --check`, wheel build и Alembic SQL проходят.

## Production rollout и rollback

Перед deployment применить новую Alembic migration. Затем обновить Vercel deployment и переподключить/обновить MCP plugin, чтобы ChatGPT увидел write-tool. Сначала выполнить один ручной запуск skill и проверить сохранённые tier на dashboard, после чего создать расписание в ChatGPT.

При rollback вернуть предыдущий deployment. Миграцию данных не откатывать автоматически, пока не проверена совместимость старого dashboard со значениями tier; при необходимости выполнить отдельную forward-fix migration. GitHub workflow не удалять в production до успешного ручного end-to-end теста новой схемы, а сначала отключить расписание или сохранить файл на время rollout.

## Решения, требующие утверждения

- Tier list: `S / A / B / C`; неподходящие вакансии не сохраняются.
- Write-tool в личной первой версии работает без полноценного OAuth, но с жёстко ограниченной мутацией только свежих канонических данных hh.ru.
- Старый GitHub/OpenAI/Resend runtime удаляется после успешной проверки нового пути.
- Skills обновляются в репозитории; пользователь самостоятельно загружает новые версии в ChatGPT и создаёт scheduled task.
