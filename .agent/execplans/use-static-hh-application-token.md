## Цель

Устранить нестабильную авторизацию relay на Vercel: все serverless-инстансы должны использовать один заранее выпущенный application token hh.ru и не обращаться к `POST /token` во время обработки запросов.

Публичные REST endpoints, MCP-инструменты и форматы успешных ответов остаются без изменений.

## Подтверждённая причина

Текущий `ApplicationTokenManager` лениво вызывает `POST https://api.hh.ru/token` в каждом процессе. Локальная блокировка предотвращает параллельную выдачу только внутри одного процесса, но не координирует независимые инстансы Vercel.

Официальная документация hh.ru указывает:

- application token необходимо сгенерировать один раз;
- повторная генерация отзывает ранее выданный токен;
- запрос нового application token чаще одного раза в пять минут возвращает `403` с `app token refresh too early`.

При масштабировании Vercel один холодный инстанс выпускает новый токен и отзывает токены тёплых инстансов. Остальные процессы пытаются выпустить следующий токен и получают запрет hh.ru. Поэтому одиночные запросы иногда успешны, а параллельный мониторинг массово получает `oauth_token_error`.

## Решение

Добавить обязательную server-side переменную `HH_ACCESS_TOKEN`. Её значение берётся из актуального application token на `https://dev.hh.ru/admin` и задаётся отдельно для нужных environments Vercel.

Relay должен:

- читать `HH_ACCESS_TOKEN` из окружения при выполнении запроса к hh.ru;
- отправлять его как `Authorization: Bearer <token>`;
- никогда не вызывать `POST /token` в runtime;
- при отсутствии переменной возвращать существующую безопасную ошибку `oauth_not_configured`;
- при отказе hh.ru в использовании токена возвращать `upstream_unauthorized` без автоматической ротации;
- не писать токен в ответы или логи.

`HH_CLIENT_ID` и `HH_CLIENT_SECRET` после миграции больше не используются и удаляются из документации и production environment. Fallback на автоматическую выдачу токена не сохраняется, поскольку он вернул бы исходную serverless-гонку.

## Изменения в коде

1. Упростить `HHClient`: убрать `ApplicationTokenManager`, запрос к `HH_TOKEN_URL`, кэширование, инвалидирование и повторную выдачу после `401`.
2. Добавить получение `HH_ACCESS_TOKEN` с возможностью явной передачи токена в тестах.
3. На `401` сразу поднимать `UpstreamUnauthorizedError`; существующие повторы transport/5xx сохранить.
4. Удалить неиспользуемую модель token response и ошибку `oauth_token_error`, если после обновления тестов на них не останется ссылок.
5. Обновить тесты клиента, REST и MCP: статический Bearer token, отсутствие вызовов `/token`, отсутствующая конфигурация, `401`, параллельные клиенты.
6. Обновить README: настройка `HH_ACCESS_TOKEN`, ручная ротация и удаление `HH_CLIENT_ID`/`HH_CLIENT_SECRET`.

## Миграция production

Порядок нужен для развёртывания без заведомо сломанной конфигурации:

1. Владелец приложения копирует актуальный application token из `https://dev.hh.ru/admin`.
2. В Vercel создаётся секретная переменная `HH_ACCESS_TOKEN` для Production и других используемых environments.
3. Развёртывается обновлённый код.
4. Проверяются `/api/health`, REST search/detail и MCP `initialize`, `tools/list`, параллельные `tools/call`.
5. После успешной проверки из Vercel удаляются `HH_CLIENT_ID` и `HH_CLIENT_SECRET`.

Значение токена не передавать в чат, Git, команды с сохраняемой историей или диагностические логи.

## Проверки

Локально выполнить:

    uv run ruff format --check .
    uv run ruff check .
    uv run pytest
    git diff --check

Тесты должны подтвердить:

- health не требует токена;
- REST и MCP используют один настроенный Bearer token;
- `/token` никогда не вызывается;
- восемь параллельных клиентов не инициируют выдачу или ротацию токена;
- отсутствие `HH_ACCESS_TOKEN` даёт `oauth_not_configured` без утечки конфигурации;
- `401` даёт `upstream_unauthorized` и не повторяет запрос с новым токеном;
- transport/5xx retries и остальные публичные ошибки не регрессируют.

После deployment повторить production-проверку восемью параллельными MCP-поисками. Критерий успеха: ни один результат не содержит `oauth_token_error` или `upstream_unauthorized`; допустимые результаты поиска имеют `isError: false`.

## Критерии приёмки

- Production relay не обращается к OAuth token endpoint hh.ru.
- Параллельные cold starts не отзывают application token друг у друга.
- REST search/detail и оба MCP-инструмента работают с существующим публичным контрактом.
- Токен отсутствует в репозитории, ответах и логах.
- Все локальные проверки проходят.
- Production smoke-проверка проходит для одиночных и восьми параллельных запросов.

## Риски и восстановление

- Неверный или отозванный `HH_ACCESS_TOKEN` остановит поиск на всех инстансах. Ошибка будет стабильной `upstream_unauthorized`, а восстановление выполняется ручной заменой переменной и redeploy.
- Ручная генерация нового token немедленно отзывает старый. Ротацию нужно выполнять согласованно: получить новый token, сразу обновить Vercel secret и redeploy.
- Секрет нельзя автоматически получить из локального контейнера. Production-настройку выполняет владелец Vercel/hh.ru; реализацию и локальные проверки можно завершить независимо.

## Решение, требующее утверждения

Переход с runtime Client Credentials на обязательный статический `HH_ACCESS_TOKEN`, ручную ротацию и удаление `HH_CLIENT_ID`/`HH_CLIENT_SECRET` после успешного deployment утверждён пользователем 2026-11-02.
