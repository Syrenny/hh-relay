# Поиск вакансий за 24 часа и полная карточка

## Цель

Упростить публичный контракт Custom GPT Action до одного сценария: поиск вакансий, опубликованных за последние 24 часа. Убрать публичное управление временем и пагинацией, перенести обход страниц и лимит внутрь сервиса, а также предоставить отдельный endpoint полной карточки вакансии.

## Подтверждённая SSR-структура

- Поиск остаётся в `vacancySearchResult.vacancies`.
- `vacancySearchResult.paging.lastPage.page` содержит индекс последней страницы, `paging.next.disabled` сообщает об отсутствии следующей страницы.
- `vacancySearchResult.criteria.items_on_page` на проверенном запросе равен `50`.
- Карточка вакансии находится в `vacancyView`.
- Подтверждённые поля карточки: `vacancyId`, `name`, `description`, `publicationDate`, `validThroughTime`, `workExperience`, `company`, `area`, `compensation`, `keySkills`, `address`, `employmentForm`, `workFormats`, `workScheduleByDays`, `workingHours`.
- `vacancyView.description` содержит HTML полного описания вакансии.
- Непустые ключевые навыки имеют подтверждённую форму `vacancyView.keySkills.keySkill` со списком строк.

## Новый публичный контракт

### `GET /api/vacancies/search`

Принимает только:

- `text` — обязательная поисковая строка;
- `area` — необязательный числовой ID региона;
- `experience` — необязательное подтверждённое значение опыта hh.ru.

Ответ содержит:

- `vacancies` — нормализованные вакансии не старше 24 часов;
- `count` — число вакансий после dedupe;
- `pages_fetched` — число реально загруженных SSR-страниц;
- `truncated` — достигнут ли внутренний предел до cutoff или конца выдачи;
- `cutoff` — timezone-aware момент `now - 24h`, использованный для фильтрации.

Параметры `hours`, `page` и `max_pages` отсутствуют в публичном endpoint и OpenAPI.

### `GET /api/vacancies/{vacancy_id}`

Принимает положительный числовой ID. Загружает обычную страницу `/vacancy/{vacancy_id}`, извлекает тот же `HH-Lux-InitialState` и `vacancyView`, возвращает нормализованную карточку с полным HTML-описанием и подтверждёнными дополнительными полями. Ответ `404` upstream преобразуется в стабильную ошибку `vacancy_not_found`; структурный drift и сетевые ошибки используют существующий формат ошибок.

## Внутренний алгоритм поиска

1. Вычислить один cutoff как `now - 24h` до первого upstream-запроса.
2. Всегда передавать upstream `page`, `enable_snippets=true` и `order_by=publication_time`. Последний параметр обеспечивает сортировку от новых публикаций к старым и делает раннюю остановку корректной.
3. Последовательно загружать страницы с нулевой, не делая лишних параллельных запросов после достижения cutoff.
4. После каждой страницы нормализовать записи, добавить вакансии с `published_at >= cutoff`, удалить дубли по `vacancyId` с сохранением порядка.
5. Остановиться, когда страница пуста, отсутствует следующая страница либо на странице встретилась органическая публикация старше cutoff. Старые рекламные вставки с подтверждённым `@isAdv=true` отфильтровываются, но не останавливают пагинацию.
6. Внутренний `MAX_SEARCH_PAGES = 10` ограничивает один запрос максимум 500 исходными вакансиями и время выполнения Vercel function.
7. Вернуть `truncated=true` только если загружено 10 страниц, cutoff/конец выдачи не достигнут и upstream сообщает о следующей странице. Во всех естественных точках остановки вернуть `false`.

## Изменения структуры кода

- Расширить upstream-модели поиска типизированным `paging`.
- Перенести цикл страниц в сервисный слой, чтобы HTTP endpoint оставался небольшим.
- Разделить parser initial state и parser конкретных `vacancySearchResult`/`vacancyView`, не дублируя `html.unescape` и `json.loads`.
- Расширить `HHClient` методами загрузки страницы поиска и карточки вакансии.
- Добавить Pydantic-модели метаданных поиска и полной карточки.
- Обновить OpenAPI metadata, README, fixture и тесты.

## Проверки

- OpenAPI поиска содержит ровно `text`, `area`, `experience`.
- Несколько страниц собираются до cutoff, ID дедуплицируются между страницами.
- Страница с публикацией на точной границе включается.
- Цикл останавливается после старой публикации и не делает следующий запрос.
- Достижение внутреннего лимита при наличии следующей страницы устанавливает `truncated=true`.
- Естественный конец выдачи устанавливает `truncated=false`.
- Detail parser возвращает полный `description` и подтверждённые поля.
- Detail `404`, `403`, timeout и структурный drift дают стабильные ответы.
- Ruff, pytest, импорт Vercel entrypoint и локальный live smoke test проходят.

## Риски

- Корректность ранней остановки зависит от `order_by=publication_time`; тест клиента фиксирует обязательную передачу параметра.
- Полное описание содержит HTML от hh.ru. Оно возвращается как данные, без серверного исполнения или преобразования; клиент должен отображать его безопасно.
- Для очень широкого запроса за 24 часа может быть больше 500 результатов. В этом случае `truncated=true` явно сообщает о неполном результате.

- 2026-08-25: live test выявил старые рекламные вставки среди свежей выдачи; остановка уточнена по подтверждённому `@isAdv`, добавлен regression test.
- 2026-08-25: реализован `GET /api/vacancies/{vacancy_id}` с полным HTML-описанием из `vacancyView` и стабильной ошибкой `vacancy_not_found`.
- 2026-08-25: Ruff проходит, 20 тестов проходят. Live поиск загрузил 8 страниц, вернул 371 уникальную вакансию и естественно достиг cutoff; detail endpoint вернул полное описание длиной 3974 символа.
- 2026-08-25: production-диагностика Custom GPT Action выявила `paging: null` для одностраничной выдачи и слишком большой ответ 333 КБ для 239 вакансий. Пользователь утвердил внутренний `MAX_SEARCH_RESULTS = 50`; `paging: null` трактуется как естественный конец, а `truncated` также сообщает о превышении лимита результата.
- 2026-08-25: повторная Action-проверка показала `ResponseTooLargeError` при лимите 50 (production payload около 71 КБ) и транзиентные `ClientResponseError`. Лимит снижен до 20, для timeout/403/429/5xx/сетевой ошибки добавлен один внутренний retry.
- 2026-08-25: замер production payload показал, что `snippet` занимает 65,6% массива вакансий. По решению пользователя `snippet` полностью удалён из поискового ответа, детали остаются в `getVacancy`; лимит результата возвращён к 50 при ожидаемом payload около 20–25 КБ.
