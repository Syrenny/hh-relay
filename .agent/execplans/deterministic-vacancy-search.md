## Цель

Полностью убрать управление поисковыми запросами из модели. Relay должен за один вызов самостоятельно выполнить фиксированную матрицу поисков hh.ru за последние 24 часа, объединить результаты, удалить дубли и уже классифицированные вакансии, затем вернуть весь оставшийся набор. Модель только читает карточки, назначает `S/A/B/C/rejected` и сохраняет классификации.

## Новый поток запуска

1. Skill начинает с вызова `search_vacancies()` без аргументов.
2. Relay загружает серверную матрицу текстов и значений опыта из настроек Neon; для новой базы использует встроенные значения по умолчанию.
3. Каждый поиск выполняется без `area`, поэтому охватывает всю доступную hh.ru географию и удалённые вакансии.
4. Relay обходит все доступные страницы каждого запроса в пределах официального API hh.ru, объединяет результаты по vacancy ID и сортирует их от новых к старым.
5. Relay исключает ID, которые уже успешно классифицированы и находятся в Neon.
6. Оставшийся список сортируется стабильно и возвращается страницами фиксированного серверного размера с непрозрачным курсором.
7. Модель классифицирует каждый возвращённый ID, сохраняет результаты через `save_classified_vacancies` пакетами не более 15 элементов и запрашивает следующую страницу до `next_cursor = null`.

Если выполнение оборвётся до сохранения, несохранённые ID снова вернутся при следующем запуске. Сохранённые исчезнут за счёт серверной дедупликации.

## Матрица поиска

Начальная матрица по умолчанию состоит из текстов:

- `Python backend`;
- `Backend Python`;
- `Python developer`;
- `Python разработчик`;
- `Junior Python`;
- `Django developer`;
- `FastAPI`.

Каждый текст выполняется для двух значений опыта:

- `noExperience`;
- `between1And3`.

Итого по умолчанию relay выполняет 14 запросов. Окно остаётся строго 24 часа. Фильтры зарплаты, работодателя, графика, формата работы и региона не добавляются. Значения по умолчанию хранятся в коде и покрываются тестом; фактическая матрица может быть изменена пользователем только через защищённые настройки dashboard. Модель и MCP-клиент не получают возможности менять её.

## Настройки в dashboard

Добавить страницу `/dashboard/settings`, защищённую существующей HTTP Basic авторизацией. На ней пользователь может:

- добавлять, изменять и удалять поисковые фразы;
- включать или выключать `noExperience`;
- включать или выключать `between1And3`;
- сохранить всю конфигурацию одной операцией.

Окно поиска показывается как фиксированные 24 часа и в этой итерации не редактируется. Регион, зарплата и остальные фильтры не добавляются.

POST настроек использует существующую проверку origin. Сервер валидирует непустой список уникальных нормализованных фраз, ограничения длины и наличие хотя бы одной категории опыта. Порядок фраз сохраняется и используется при выполнении запросов. Интерфейс остаётся server-rendered и не зависит от JavaScript для сохранения.

На главной странице dashboard добавить компактную ссылку «Настройки». После сохранения показывать понятный результат либо перенаправлять обратно на страницу настроек без вывода секретов.

## Данные и migration

Добавить Alembic migration с singleton-настройкой поиска. Хранить список фраз и выбранные значения опыта в типах PostgreSQL, подходящих для атомарной загрузки и обновления одной конфигурации. Не хранить в настройках секреты или произвольные параметры hh.ru.

При отсутствии строки настроек сервис использует матрицу по умолчанию из кода. Migration может создать начальную строку с теми же значениями, но runtime не должен ломаться при её отсутствии. Обновление выполняется одной транзакцией.

## Изменение контрактов

Старый параметризованный поиск удаляется:

```text
search_vacancies(text, area?, experience?)
```

Вместо него остаётся детерминированный метод:

```text
search_vacancies(cursor?) -> SearchResponse
```

`cursor` является единственным входным параметром и не позволяет модели влиять на поисковые условия. `SearchResponse` возвращает страницу объединённого набора, `next_cursor` и диагностические поля, полезные для проверки полноты. Невалидный курсор отклоняется явной безопасной ошибкой. `get_vacancy` и `save_classified_vacancies` не меняются.

Параметризованный REST endpoint `/api/vacancies/search` также переводится на контракт, принимающий только необязательный `cursor`, чтобы у relay не оставалось второго публичного способа передавать произвольные поисковые запросы. Неиспользуемая модель `SearchQuery` удаляется.

Это намеренно несовместимое изменение. После deployment клиенту MCP потребуется обновить metadata или начать новую Codex-сессию, чтобы увидеть новую входную схему tool.

## Реализация поиска

- Вынести значения матрицы по умолчанию в явные типизированные константы рядом с поисковым сервисом.
- Перед поиском загрузить одну валидированную конфигурацию из Neon; при отсутствии использовать значения по умолчанию.
- Для каждой пары текста и опыта вызвать официальный hh.ru API с `date_from/date_to` и `order_by=publication_time`.
- Обойти все страницы, заявленные ответом hh.ru, без текущего `MAX_SEARCH_RESULTS = 50`.
- Сохранить защиту от повторяющихся ID внутри одного запроса и добавить дедупликацию между всеми 14 запросами.
- Ограничиться пределами пагинации официального API; если upstream сообщает недоступное продолжение или меняет структуру, вернуть явную ошибку, а не молча неполный результат.
- После объединения одним запросом к Neon исключить уже классифицированные ID.
- Сортировать по `published_at DESC, id DESC`, применять непрозрачный курсор по этой паре и возвращать страницу фиксированного размера.
- Не отмечать вакансии обработанными до успешного `save_classified_vacancies`.
- Не менять допустимый возраст сохранения: текущий предел 48 часов остаётся защитным запасом, а поиск выдаёт только последние 24 часа.

## Критерии приёмки

- Модель не передаёт relay ни текст запроса, ни регион, ни опыт.
- Последовательность вызовов по `next_cursor` покрывает всю сохранённую серверную матрицу за 24 часа; новая база по умолчанию получает 14 комбинаций.
- Пользователь может изменить фразы и категории опыта через защищённый dashboard без изменения кода и без передачи управления модели.
- Возвращаются все уникальные ещё не классифицированные вакансии, доступные через выполненную матрицу, без лимита 50.
- Уже сохранённые `S/A/B/C/rejected` не возвращаются повторно.
- Частично обработанный запуск не теряет несохранённые вакансии.
- Skill классифицирует и сохраняет весь полученный набор.
- Старый параметризованный контракт отсутствует в MCP metadata и OpenAPI.
- Все тесты, линтеры, сборка и smoke test проходят.

## Итог реализации

`search_vacancies` больше не принимает поисковый текст, регион или опыт. Единственный необязательный аргумент — непрозрачный `cursor`. Relay загружает настройки из Neon, выполняет матрицу с ограниченным параллелизмом, обходит все страницы hh.ru за 24 часа, дедуплицирует ID, исключает уже классифицированные вакансии и возвращает страницы по 30 элементов.

Добавлена migration `20261113_04` и защищённая страница `/dashboard/settings`, где редактируются поисковые фразы и две допустимые категории опыта. Начальная конфигурация содержит 7 фраз и 14 комбинаций. REST/OpenAPI и MCP используют единый поток поиска.

Skill больше не формирует запросы: он проходит `next_cursor` до конца, классифицирует каждую вакансию и сохраняет страницы batch-вызовами до 15 элементов. `get_vacancy` и `save_classified_vacancies` не изменены.
